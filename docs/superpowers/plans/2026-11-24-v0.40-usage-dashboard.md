# v0.40 Task 11 — Usage dashboard per agent

Status: plan. GoAhead feature, not an upstream port. No migration, no schema change.

## Goal

A Usage tab in Settings shows, for the last 7 or 30 local days, on this computer only:

- tokens per day for each agent and provider,
- cached input against uncached input,
- the top agents by tokens,
- the routine runs that a run condition skipped,
- an empty state.

The backend gives `usageByAgent(range): AgentUsageSummary[]`. Tasks 12 and 13 reuse it to show savings.

## What the database stores (findings)

`agent_usage_records` (migration 15) holds one row for each usage report:
`agent_id, record_id, session_id, turn_id, provider, model, occurred_at, tokens_json, estimated_cost_usd,
rate_basis, recorded_at`. `tokens_json` is `{uncachedInput, cachedInput, cacheCreation, output}`; a key
can be `null` when the provider did not report it.

**The rows are deltas, not cumulative totals.** The providers report cumulative counters for each session
(Codex `thread/tokenUsage/updated` total, Claude `modelUsage` from the SDK result, ACP `usage`).
`AgentUsage.record` (`src/backend/database/agent-usage.ts`) keeps the last cumulative value for each
`(agent_id, counter_id)` in `agent_usage_checkpoints`, and writes only `max(0, current - previous)` for each
key to `agent_usage_records`. So:

- **Sum of rows = usage.** No row repeats tokens of an earlier row of the same counter.
- **Resumed session.** The counter id is stable for a session: Codex `${session.id}:codex`, Claude
  `${session.id}:${threadId}:${model}`, ACP `${session.id}:grok`. A resumed session finds its checkpoint and
  writes only the difference. A resumed Claude session with no checkpoint (from before stable counter ids)
  is written as a baseline: the checkpoint is set and no row is written. When the Claude totals restart from
  zero, the client takes a new random counter id, so the new totals are not subtracted from old ones.
- **Same report twice.** `record` runs through `DatabaseCore.dispatch` with the command id
  `analytics:<agent>:<sha256(counter, turn, tokens, cost)>`. A second identical report finds the receipt and
  writes nothing.
- **Missing provider.** Every provider writes to the same table with its own `provider` value. The
  aggregation groups by the stored `provider` string and has no provider list, so a provider that this build
  does not know still counts.

The aggregation therefore sums the stored rows. It does not compute differences again.

**Weekly budget (fix round 1).** An agent can have `AgentSummary.weeklyTokenBudget`
(`AGENT_WEEKLY_TOKEN_BUDGETS`). `AgentTokenBudget` (`src/main/agent-token-budget.ts`) alerts at 80% and 100%.
Its week starts on Monday 00:00 in the computer's time zone, and it measures
`getAnalytics({agentId, startDate: Monday, endDate: today, timeZone}).totals.processedTokens`. The week
helpers and the levels moved, unchanged, to `ipc-usage-dashboard.ts` (`computerLocalDate`,
`tokenBudgetWeekStart`, `tokenBudgetWeekInput`, `TOKEN_BUDGET_ALERT_LEVELS`, `tokenBudgetLevel`). The alert
and the dashboard (`src/backend/agent/weekly-token-budget.ts` `weeklyBudgetUsage`) both build the request with
`tokenBudgetWeekInput` and read the same `AgentService.getAnalytics`, so they share one source.

**Not stored:** the provider usage limit state (`UsageLimitGate`) is an in-memory map, with no history. So
"agents that hit a provider limit in the range" is left out.

## Skipped runs (findings)

v0.39 run conditions (`src/backend/agent/routine-scheduler.ts#skipByRunCondition`,
`src/backend/channel-routine-scheduler.ts#runConditionSkip`) record a skipped scheduled run as a run with
`status = 'cancelled'` and `error = sourceText(key)`, where the key is
`error.backend.routineRunConditionUnchanged` or `error.backend.routineRunConditionNotMet`. `sourceText` is
always English and must stay byte-identical, so the two texts identify these runs. Other cancelled runs have
a different error (missed runs) or `NULL` (limit policy "skip", user cancel). The count uses
`scheduled_for` (the occurrence time; the check runs at that time).

Agent routine runs (`projection_routine_runs`) have `agent_id` and count for the agent. Channel routine runs
(`projection_channel_routine_runs`) have no agent, so the dashboard shows them as one separate count.

## Local day boundaries

The range is `{ days: 7 | 30, endDate: "YYYY-MM-DD", timeZone }`. The renderer sets `endDate` to today in
the user's time zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`), as `analyticsRange` does. The
backend sets `startDate = endDate - (days - 1)`.

SQLite cannot convert to an IANA zone. So the query reads rows with `occurred_at` (or `scheduled_for`) in
`[startDate - 1 day, endDate + 2 days)` UTC, which covers every offset from UTC-12 to UTC+14. Then each row's
timestamp goes through `analyticsDate(date, timeZone)` (the same `Intl` formatter as the host report), and
only rows with `startDate <= localDate <= endDate` count. A daylight-saving change does not matter, because
each timestamp is converted on its own.

## Interfaces

`packages/contracts/src/ipc-usage-dashboard.ts` (exported from `@openbot/contracts/ipc`):

```ts
type UsageDashboardDays = 7 | 30;
interface UsageRange { days: UsageDashboardDays; endDate: string; timeZone: string }
interface UsageProviderDay {
  date: string; provider: string;
  uncachedInput: number; cachedInput: number; cacheCreation: number; output: number; totalTokens: number;
}
interface AgentUsageSummary {
  agentId: string;
  uncachedInput: number; cachedInput: number; cacheCreation: number; output: number; totalTokens: number;
  incompleteRecords: number;   // rows with a null key; the known keys still count
  skippedRuns: number;         // agent routine runs skipped by a run condition
  daily: UsageProviderDay[];   // one cell per local date and provider with a row; sorted by date, provider
}
interface UsageDashboard {
  days; startDate; endDate; timeZone;
  agents: AgentUsageSummary[]; // most tokens first, then agent id
  skippedChannelRuns: number;
  weeklyBudgets: AgentWeeklyBudgetUsage[]; // every agent with a budget; over budget first
}
interface AgentWeeklyBudgetUsage {
  agentId: string; budgetTokens: AgentWeeklyTokenBudget; usedTokens: number;
  level: 80 | 100 | null; weekStart: string;
}
function usageRange(days, now?): UsageRange;          // renderer: today in the local zone
function usageRangeStart(range): string;             // endDate - (days - 1)
function parseUsageRange(value: unknown): UsageRange; // main: decode the IPC payload
function decodeUsageDashboard(value: unknown): UsageDashboard; // preload: decode main's answer
```

## SQL

```sql
-- tokens (index agent_usage_occurred)
SELECT agent_id, provider, occurred_at, tokens_json FROM agent_usage_records
 WHERE occurred_at >= ? AND occurred_at < ?;
-- agent runs skipped by a run condition
SELECT agent_id, scheduled_for FROM projection_routine_runs
 WHERE status = 'cancelled' AND error IN (?, ?) AND scheduled_for >= ? AND scheduled_for < ?;
-- channel runs skipped by a run condition
SELECT scheduled_for FROM projection_channel_routine_runs
 WHERE status = 'cancelled' AND error IN (?, ?) AND scheduled_for >= ? AND scheduled_for < ?;
```

## Tests

`src/backend/usage-by-agent.test.ts` (Node, real SQLite through `OpenBotDatabase` and `AgentRoutineStore`):

1. A resumed session and two providers: cumulative Codex counter reported three times (one repeat), the
   session resumed with the same counter, and a Claude session with two models. Exact totals per agent,
   provider and day.
2. Cached against uncached input: exact `cachedInput`, `uncachedInput`, `cacheCreation`; a row with a null
   key counts its known keys and adds one to `incompleteRecords`.
3. The 7-day and 30-day boundaries in `Asia/Tokyo` and the UTC padding: rows one second inside and outside
   each local midnight.
4. Skipped runs: two run-condition skips count, a limit-policy cancel and a run outside the range do not;
   channel skips are separate.
5. Empty state: no rows gives `[]` and zero channel skips.

`src/main/agent-token-budget.test.ts` (Node, real SQLite): 85% is warned (80), 100% is over, an agent with no
budget is not listed, a row on Sunday 23:59:59 local is the previous week and Monday 00:00 is this week, and
the alert and the dashboard give the same tokens and levels for the same rows.

`packages/ui` empty state: `src/renderer/src/features/settings/SettingsUsageTab.test.tsx` (jsdom) renders the
shared panel with an empty dashboard and checks the empty text.
