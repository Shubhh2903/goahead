# v0.40 Task 12: Cheaper hand-offs between agents

## Step 0: what a hand-off costs today

Sources: `src/backend/agent/openbot-tool-router.ts` (send_message), `src/backend/mailbox-store.ts`
(enqueue, `nextQueued`, `#isHeldReply`, `repliesToStartWith`), `src/backend/agent/drain-scheduler.ts`
(`startDelivery`), `src/backend/agent/delivery-content.ts` (`deliveryPromptInput`,
`combinedPromptInput`), `src/backend/agent/turn-lifecycle.ts` (`#finishTurn`, `#relayAgentResult`),
`src/backend/agent/developer-instructions.ts`.

### Trace: A calls `send_message` to B, B answers

1. A's turn calls `openbot.send_message`. The router validates the input and calls
   `MailboxStore.enqueue` with idempotency key `<threadId>:<turnId>:<callId>`. Files in `paths` are
   copied into the managed transfer folder (by reference, not inline). The tool result is the JSON
   receipt (about 200 characters). A's turn continues; it does not wait.
2. B's drain starts a new turn for B (`startDelivery`). B receives `deliveryPromptInput`:
   - a frame of 824 characters (sender, message id, the Status/Result/Evidence reply protocol),
   - the message text (at most 100,000 characters, from the tool schema and `INPUT_LIMITS.messageText`),
   - attachments as `localImage` / `mention` items with a local path, plus one list line each.
   B does **not** receive A's context, A's transcript, or file bytes inline. The only history copy
   is the provider-switch hand-off (`handoff-history.ts`), which is for B's own thread, not for A.
3. B's turn ends. If B did not call `send_message` with a reply, `#relayAgentResult` enqueues B's
   last answer to A (`expectsReply: false`, key `auto-result:<turnId>:<messageId>`). If B did reply,
   the relay is skipped (`hasReplyFrom`, `hasAgentMessageFromTurnTo`). So exactly one answer goes back.
4. The answer is a queued delivery to A. When A is idle, the drain starts a **new full turn** for A.
   When A is busy, the answer waits in the queue (agent messages never steer) and starts a turn after
   A's turn ends. A receives a frame of 892 characters plus the answer text.
5. Batching that exists already: answers to **one** multi-recipient message wait until every recipient
   is done (`#isHeldReply`), and then start **one** turn (`repliesToStartWith`). A person's message
   takes the held answers with it.

### Turn counts and payloads (before)

Base cost of one A turn: about 7.7K tokens of fixed instructions and tool names (measured 2026-10-14),
plus A's thread, which grows to the compaction window (80K–120K tokens). Most of it is cached input,
but cached input still counts toward plan capacity. Estimate: 20K–80K input tokens for each A turn.

| Scenario | B turns | A turns caused | Frame (chars) |
| --- | --- | --- | --- |
| A asks B (one request) | 1 | 1 | 824 to B, 892 to A |
| A asks B and C in **one** send_message | 2 | 1 (already batched) | 824 each, 1,857 for two answers |
| A asks B and C in **two** send_message calls in one turn | 2 | **2** | same |
| A asks N teammates in N calls in one turn | N | **N** | same |
| B's answer is longer than 100,000 characters | 1 | **0, the answer is lost** | — |

The last row is a bug: `enqueue` throws `error.agent.messageTooLong` inside `#finishTurn`. The rest of
`#finishTurn` does not run (no queue event, no `turn-completed`, no drain of B), and A never gets an
answer.

### What is already lean

- B gets a short brief: the frame plus the message text, and file references. There is no context
  copy to remove. Making the frame shorter saves about 200 tokens per hand-off: less than 1% of one
  turn. Not worth the prompt-behavior risk.
- An answer must wake A when A has to act on it (orchestration, the next step). The code cannot know
  when A only "shows" the answer, so a no-wake path would break the orchestrator flow. Not done.

## Changes (the ones that save turns with low risk)

1. **One turn for all answers to one fan-out.** Treat all requests that A sent in **one turn**
   (same sender, same source turn id from the idempotency key) as one request group. An answer waits
   while another request of the group is still queued, starting or running at another teammate,
   exactly like the existing multi-recipient hold. The answers then start one turn together.
   A person's message still takes the waiting answers with it. Teammates whose request of the group
   ended with no answer are named in that turn, as today.
   Saves N−1 A turns for N separate requests in one turn (20K–80K input tokens each).
   - `MailboxStore`: a private `#requestGroup(request)`; `#isHeldReply` and `repliesToStartWith`
     use it; public `requestGroupIds(requestId)` for the drain.
   - `DrainScheduler.startDelivery`: the "no answer comes from" list reads the whole group.
2. **Bound the relayed answer.** `#relayAgentResult` shortens an answer above
   `INPUT_LIMITS.messageText` and adds a one-line note that the full answer is in B's conversation.
   B's own conversation keeps the full text. This removes the lost-answer bug and gives the
   hand-off payload a hard size bound.

No schema, migration, IPC, or Team API change. The idempotency map is already persisted, so the
group survives a restart. `ALWAYS_LOADED_OPENBOT_TOOLS` and tool descriptions do not change.

## Risks

- An answer can wait longer: until the slowest request of the same turn ends. The multi-recipient
  hold already accepts this. A person's message releases the waiting answers.
- A request held at a teammate whose plan limit is spent holds the group's answers until the reset,
  as today for one multi-recipient message.

## Tests

- `mailbox-store.test.ts`: answers to two requests from one turn are held until both end and then
  start together; a request from another turn does not hold them.
- `agent-service.routines.test.ts`: two requests from one turn give A exactly one turn, with both

- `agent-service.routines.test.ts`: an answer longer than the limit still reaches A once, shortened.
- Existing: an answer that needs the caller to act still wakes it (relay test).

## Result (after)

| Scenario | A turns before | A turns after | Payload bound |
| --- | --- | --- | --- |
| A asks B (one request) | 1 | 1 | frame 824 / 892 chars + text ≤ 100,000 |
| A asks B and C in one send_message | 1 | 1 | same |
| A asks B and C in two send_message calls in one turn | 2 | 1 | frame 1,857 chars for two answers |
| A asks N teammates in N calls in one turn | N | 1 | about 900 chars of frame per answer |
| B's answer is longer than 100,000 characters | 0 (lost) | 1 | relayed text ≤ 100,000 chars |

Saving: N−1 A turns per fan-out, about 20K–80K input tokens each (estimate, not measured in the app).
