# v0.40 Task 15: Android notification buttons

Goal: Approve, Deny and Open buttons on the Android live-update notification, with the same signed
action links and the same checks as the iPhone Live Activity.

## How iPhone works now

1. The host (`src/main/live-activity-push.ts`) or the phone builds `AgentLiveActivityProps` with
   `liveActivityView`. `liveActivityButtons` makes the buttons. Each button URL is
   `goahead://live-activity?action=<json>&sig=<hmac>`, from `liveActivityActionUrl`. The JSON holds
   the action (`serverId`, `agentId`, `requestId`, decision or answers) and, for Approve, the command.
   The signature is `signLiveActivityLink` with the `action` key of that host. Only the phone and
   that host have the key; the widget does not.
2. A tap opens the app. `+native-intent.tsx` calls `liveActivityRoute`, which calls
   `readLiveActivityLink`. It takes the key of the server that the action names and checks the
   signature. A wrong signature, an unknown server, or no key gives `{ type: "list" }`: the app
   opens, and nothing happens. A link that comes before the keys load is checked when they load.
3. `use-live-activity.ts` gets the request. It waits for the server to be online. Approve shows a
   confirmation alert with the signed command first. Decline and question answers run at once.
4. Binding: the signature covers server, agent, request id and decision. Replay: the link has no
   nonce and no expiry. A second tap sends the same answer again, and the host refuses an answer to a
   request that is gone. Sign-out makes a new phone secret, so old links stop verifying.

## Android design

- No wire change. The host already seals the whole props, with the signed `buttons`, into the FCM
  message of `android-live-update-push-v1`. The v0.39 phone reads only the fields it shows and
  ignores `buttons` (see `parseView`). So the desktop does not change, and no new capability is
  needed. This keeps the released meaning: the payload is the same sealed props.
- The phone reads `mode` and `buttons` from the props (host or app). Only `approval` and `question`
  (a prompt waits) get buttons. Other modes get no category and no buttons. The `failed` mode "Open
  details" button of iPhone is not shown, because a failure is not a waiting prompt; a tap still
  opens the chat.
- Buttons: the signed buttons of the props (Deny, Approve when the command fits; or up to three
  answers), then Open (the unsigned tap link) when Android has room (at most 3 actions).
- `expo-notifications` 57 supports Android actions: `setNotificationCategoryAsync` and
  `categoryIdentifier`. Android reads the category when it shows the notification, so the phone
  sets the category of the mode with the current labels just before each show. No native change.
- Every action has `opensAppToForeground: true`. A tap never acts in the background. The response
  listener maps the action id to the URL in the notification data and opens it with `Linking`, so
  it goes through the same `liveActivityRoute` and `readLiveActivityLink` as iPhone, and Approve
  gets the same confirmation in the app. An action URL that is not a Live Activity link is not
  opened; the app opens the tap link instead.
- Notification data holds the signed URLs, as the iPhone content state does. It holds no key.
