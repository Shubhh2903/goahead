# Phone connection status (v0.40, task 14)

Goal: the server row on the phone shows how the phone reaches the desktop, or why it cannot.
Client-side only. No Team API wire change. No desktop change.

## Today
- `remote-peer.ts` `reportRoute` reads `getStats()` after `connected` and sends a `route`
  diagnostic as text (`host/udp -> srflx/udp`) to the support log only.
- The Signal `ready` message gives `iceServers`. A TURN entry is there only if the relay is configured.
- v0.39 adds a public STUN URL (`PUBLIC_STUN_URLS`) in that same `iceServers` list.

## Design
1. `packages/team-client/src/connection-path.ts` (pure, no platform code):
   - `connectionPathFromCandidates(local, remote)` returns `direct`, `relay`, or `null`.
   - `connectionFailureReason(facts)` returns a reason code.
2. `remote-peer.ts` keeps facts it really has (ICE server URLs, whether a `srflx` candidate was
   gathered, whether Signal ever sent `ready`) and calls a new optional action
   `onConnectionPath({ hostId, path })`:
   - on `connected`, from the selected pair (reuses the `getStats` read of `reportRoute`);
   - on ICE `failed` before authentication, or on the 30 s connect timeout, as `cannot-connect`;
   - on Signal closed before it was ever ready, as `cannot-connect` / `signal-unreachable`.
   The raw text `route` diagnostic stays as it is. The action is optional, so the web bridge and
   old callers do not change.
3. Mobile: `ServerConnection` filters by `hostId` and passes the path up; the workspace context
   stores it on `MobileServer.connectionPath`; the server drawer row shows the label.
   Text: `mobile.workspace.connectionPath.*` en keys.

## Mapping table (candidate types of the selected, nominated, succeeded pair)
| local | remote | status |
| --- | --- | --- |
| host / srflx / prflx | host / srflx / prflx | Direct |
| relay | any | Relay |
| any | relay | Relay |
| unknown or missing | any | no status (no guess) |

## Failure reasons (only from facts the client has)
Checked in this order, when ICE failed before authentication or the connect timeout hit:
| fact | reason | text |
| --- | --- | --- |
| Signal never sent `ready` | signal-unreachable | Cannot connect: server not reachable |
| no `stun:`/`stuns:` URL in `iceServers` | no-stun | Cannot connect: no STUN server |
| STUN listed, no `srflx` candidate gathered | stun-unreachable | Cannot connect: STUN server not reachable |
| no `turn:`/`turns:` URL in `iceServers` | no-relay | Cannot connect: no relay. Try the same Wi-Fi. |
| TURN listed, still failed | no-path | Cannot connect: no network path found |

"no-relay" is the likely symmetric-NAT case on mobile data. The text does not claim a NAT type.
A later TURN option is named only by the "no relay" wording; no promise is made.

## Older desktops
Nothing is sent or read on the wire that is new. The candidate pair is local to the phone WebRTC
stack, so every desktop version works the same.

## Display rules
- Online server: `Local · Direct` or `Local · Relay`. No path yet: no suffix.
- Offline server with `cannot-connect`: `Cannot connect: <reason>` alone (the row is one line).
- A stale `cannot-connect` never shows on an online or connecting server.
